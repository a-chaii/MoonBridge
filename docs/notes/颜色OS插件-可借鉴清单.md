## 1. 定位差异（决定学什么 / 不学什么）

| | FxxkMoondrop | 我们 |
|---|---|---|
| 定位 | 想完全替代官方 App | 注入/补全宿主卡片的小插件 |
| 身份 | 蓝牙连接的「主人」 | 寄生的「房客」 |
| 结论 | 自己管连接生命周期、通知、UI | 借宿主的连接与入口，用完就退 |

**推导出的两条硬约束：**
1. 不常驻占用 GATT，避免与官方 App / 宿主抢连接（空闲即断、按需重建）。
2. 不自建通知 / EQ / 独立 Activity —— 一旦做就从「插件」变成「半替代品」，维护面和冲突面都会膨胀。

## 2. 当前自动弹窗的实现现状（含缺陷）

```
触发：A2DP / HFP CONNECTION_STATE_CHANGED 或 ACL_CONNECTED 广播
      → 校验 MAC ∈ {24:01:30:B5:58:22, 24:01:30:B5:0D:22}
      → fire() → 延迟 900ms → startActivity(panel intent)
```

**已知缺陷（待改）：**
- `TITLE = "Moondrop Golden Ages 2"`、`MODEL_ID = "sAlm"`、`MACS` **全部硬编码** → 换一副耳机就不弹了；弹出来也永远是梦回 2 的标题。
- 触发依赖「profile 已连接」，这是整条链路里最慢的一环（A2DP 建链本身就要几秒）。

## 3. Fast Pair 提速（最有价值的借鉴项）

**为什么快**：Fast Pair 在设备进入可发现/配对阶段就能拿到 `model id` + 地址，早于 A2DP/HFP 建链。我们等的是「链路成立」，他等的是「设备出现」。

**落地方式（两段式）**
1. 补全 ColorOS 上被砍掉的 GMS Fast Pair 组件（已验证有效）；
2. 在模块里 hook Fast Pair 的发现回调/广播，拿到 `model id + address`：
   - 命中水月雨 model id → **提前**发 panel intent（此时可能链路还没完全就绪）
   - 与现有 profile 广播触发共用同一套去重（现成的 `dedupeWindow`，20s 窗口）

**注意**
- 缺 GMS 的机型要能降级回现有广播触发，不能因为拿不到 Fast Pair 就不弹。
- `fire()` 里的 `CONNECT_DELAY_MS = 900ms` 在 Fast Pair 路径下应该缩小甚至归零（它本来就是为了等链路）。

## 4. GATT 是什么（知识条目）

**GATT = Generic Attribute Profile**，BLE 之上的「属性表」协议。BLE 设备把自己的能力组织成一张表：

```
Service（服务，按 UUID 区分功能，如「电池服务」「GAIA 服务」）
 └── Characteristic（特征，实际数据点）
      ├── 属性：Read / Write / WriteNoResponse / Notify
      └── Descriptor（描述符，常用来订阅通知 CCCD）
```

操作方式只有四种：**读、写、订阅通知（notify/indicate）、读描述符**。没有「请求-应答」这种语义，所以「发一条命令再等回包」要自己用「写特征 + 订阅通知特征」两件事拼出来。

**我们项目里的用法（GAIA over GATT）**
- 写特征：发命令帧（`00 1D 1A 01 01 02` 这类裸 PDU）
- 通知特征：收回包（`00 1D 1B 01 01 64 02 64`）
- 这就是 `GaiaGattTransport` 干的事，也是代码注释里写的「唯一能收到回包的那条」。

**和 SPP / RFCOMM 的区别**

| | BLE GATT | SPP / RFCOMM |
|---|---|---|
| 形态 | 属性表，有边界明确的通知包 | 串口式字节流，没有消息边界 |
| 收包 | 天然按通知分帧 | 会粘包/半帧，**必须自己切帧** |
| 典型设备 | GAIA V3（我们主力路径） | GAIA V4（如布丁） |

> 这也解释了上游为什么专门写了一个 `GaiaRfcommFramer` 流式状态机 —— 那是 SPP 才需要的补丁，BLE 路径不需要。

## 5. 可借鉴清单（按优先级，含适配判断）

### ★★★ 直接决定「能不能支持全系」
| 项 | 做法 | 为什么不学不行 |
|---|---|---|
| **能力探测优先于型号猜测** | 读 GAIA feature bitmap：`F_ANC_V2(0x20)` / `F_AUDIO_CURATION(0x08)` / `F_SPATIAL(0x18)` 决定显示哪些功能 | 没有设备实测时，靠型号名匹配是**不可验证**的；能力探测是设备自己报的 |
| **三协议自动路由** | GAIA V3(BLE) / V4(SPP) / 9ECA 私有 自动识别 | 全系兼容的前提 |
| **映射表单测** | 上游那 26 个 profile 解析/方向单测一起移植 | 没有实机时**唯一**的验证手段，能防「数组顺序抄错导致全系错档」 |
| **Fast Pair 发现源** | 见第 3 节 | 弹窗速度 6s→2.5s 就靠这个 |

### ★★ 提升稳定性
| 项 | 做法 |
|---|---|
| 超时/重试/错误码状态机 | 我们现在多处裸 `Thread.sleep`，整理成小状态机 |
| 指纹去重思想 | 上游用在通知；我们可用于「防重复弹窗 / 防重复刷新导致布局抖动」 |
| RFCOMM 流式切帧 | **仅当**决定支持 SPP 设备时才需要 |

### ★ 或有或无
- 无 Root 模式 → 不适用（我们本来就是注入）。

### 明确不学
- 自带常驻通知、EQ 编辑器、独立 Activity
- 常驻 GATT 连接
- GMS Fast Pair 的**弹窗 UI** 部分（我们用自己的卡片，不重画 Fast Pair 半屏）

## 6. 已被否决的方案（别再提）

- **读缓存预渲染**：打开卡片先显示上次电量/档位。否决理由：**太容易误导**（显示的是过去的状态，用户会当成当前值）。
- 由此推论：任何「拿旧值顶替实时值」的做法都不做，宁可显示 `电量 --`。

## 7. 待办（等有空再动手，按推荐顺序）

1. **去掉 AutoPopup 的硬编码**：`TITLE` / `MODEL_ID` / `MACS` 改为从广播设备信息 / 配对数据 / 宿主 intent 动态取；未知设备也要能弹（标题用系统名）。
2. **Fast Pair 作为第二触发源**：命中即提前弹，与 profile 广播共用去重。
3. **能力探测**：连上先读 feature bitmap，按能力决定卡片显示哪些行。
4. **三协议路由** + 移植映射单测。
5. 若决定支持 SPP 设备，再搬 RFCOMM 切帧。
